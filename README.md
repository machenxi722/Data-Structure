## 清单如何使用

- 每个考点有固定编号，例如 `DS02-001`。编号用于题目注释和链接，已有编号不重排、不复用。
- “代码”栏的 `—` 表示尚未关联自己提交的代码；有代码后直接替换为文件链接，同一考点可关联多份代码。
- 概念、性质、手工推演和复杂度分析同样属于考点，并非每项都必须单独写程序。有代码链接也不代表已通过测试或已经掌握。
- 课件中的例题、习题涉及的算法方法一并列入；相同方法的重复演示合并。`【扩展】`表示课件带星号或明确拓展的内容，不自行推断是否必考。
- 每章的 `F1`、`F2` 等对应本章资料表。页码从该文件的第一张幻灯片/第一页起算，包含封面，与课件印在页面上的页脚编号可能不同。
- PPT、PDF 原件保留在本地原目录，不纳入 Git；GitHub 保存考点清单和后续提交的代码。资料表中的课件名用于本地查找。

## 后续收到编程题的处理流程

每次开始本项目任务，先读本 README，再读涉及章节的 README。

1. 阅读用户提供的题目和代码，判断主章节及所有实质涉及的考点。缺少题面时以代码可确认的信息为准，不补造题意或输入限制。
2. 将代码归入主章节的 `code/` 目录，一道题只保留一份正式文件，例如 `7树和二叉树/code/P0001_二叉树层序遍历.cpp`。题号全仓库唯一；分配前检查所有 `code/` 目录的已有题号。保留原语言和扩展名，多种解法可用 `_递归`、`_迭代` 等后缀区分。
3. 直接在代码文件顶部补充简短中文注释：题目名称、考察的考点编号与名称、核心思路、关键边界；复杂度在能从代码明确判断时注明。代码关键位置补充有助于理解的注释，避免逐行翻译语句。
4. 保留用户的算法与行为，不自行重写、优化或修复代码。阅读时发现明显问题，可用准确的注释标明并在回复中指出；用户明确要求修改时再按要求处理。
5. 在每个相关章节的对应考点“代码”栏添加相对路径链接。同一道题跨章节时，所有链接指向主章节的同一文件。只关联实际考察的知识点，不把所有基础语法和先修知识都算作覆盖。
6. 更新已有题目时保留题号与文件路径；确需改名或移动时同步所有引用。不为单题创建 README，不创建专门的查漏补缺、掌握状态或测试报告板块。
7. 按用户约定不编译、不运行代码、不执行测试，也不声称通过验证。文档路径、考点编号与本次提交范围仍须保持正确。
8. 保留已有远端历史，只提交本任务相关的文档和代码至 `main`，不强制推送、不覆盖用户无关改动。上传后简短报告代码位置和关联考点；失败时明确说明实际状态。

用户发来新代码并要求整理时，按上述流程直接归档、注释、关联并上传，无需重复询问已确定的组织规则。

## 代码注释示例

以下仅展示格式，实际题号、考点编号和说明须根据题目与当前清单填写：

```cpp
/*
 * 题目：Pxxxx 题目名称
 * 考察知识点：DSxx-xxx 考点名称；DSyy-yyy 考点名称
 * 思路：简要说明这份实现采用的算法。
 * 关键点：说明指针含义、循环条件或需要留意的边界。
 * 复杂度：仅在能够明确判断时填写，并说明 n 等变量含义。
 */
```

## 资料维护

新增课件或老师补充内容时，先核对原清单，再在相关小节补充考点和出处。新考点使用该章尚未使用的编号，已有代码链接继续保留。课件编号不一致时按主题归类，以文件名和实际页序定位；明显表述问题不照搬成结论。
